Permissioned Domains

Permissioned Domains allow account owners to define controlled access rules for specific XRPL features (e.g., trading on a DEX, participating in lending pools, or using permissioned payment channels). They reference Credentials or other proofs that users must hold to interact with the domain's resources.

🌐 Create / Update Domain PermissionedDomainSet
DomainID ✅ Required (unique identifier, often hash or short name)
Owner ✅ Implicit (your account)
AcceptedCredentials ✅ Required (array of Credential IDs or types)
Flags / Metadata ➕ Optional (description, URI, access level)
🗑️ Delete Domain PermissionedDomainDelete
DomainID ✅ Required (to identify domain to remove)
Signer ✅ Must be the owner (or authorized delegate)
Conditions ✅ No active dependencies blocking deletion
📝 Important Notes:
  • Requires the PermissionedDomains and usually Credentials amendments to be enabled on the network.
  • Each Permissioned Domain object counts toward the owner's owner reserve (~0.2 XRP) until deleted.
  • AcceptedCredentials lists which credentials (by ID or type + issuer) grant access — users must hold and present an accepted credential to interact with the domain's features.
  • Domains are owned by the creating account; only the owner (or authorized delegate) can update or delete them.
  • Common use cases: gated DEX trading pairs, permissioned lending markets, restricted payment channels, or private token swaps.
  • Metadata (URI, description) can point to off-chain rules or documentation explaining the domain's purpose and requirements.
  • Deleting a domain removes the access rules — any dependent features (e.g., gated offers) may become inaccessible or revert to default behavior.

⚠️ Irreversibility & Compliance Risks

Permissioned Domains enforce strict access control — misconfiguration can permanently block intended users or expose compliance issues.

  • Once users rely on a domain for access, **deleting or changing it** can immediately revoke permissions — plan revocation strategies carefully.
  • Incorrect or overly restrictive credential requirements can make the domain unusable — test with sample credentials before going live.
  • All domain data (including accepted credential lists) is **public on the ledger** — avoid including sensitive rules or personal data in metadata.
  • Reserve remains locked until deletion — if you forget to delete unused domains, you continue paying owner reserve indefinitely.
  • Dependent on Credentials amendment — if credentials are revoked or issuers change policies, domain access can break unexpectedly.
  • Always test creation, updates, credential checks, and deletion on devnet or Testnet first — wrong DomainID formats or missing credentials cause transaction failure and fee burn.

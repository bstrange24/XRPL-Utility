Decentralized Identifiers (DID)

Decentralized Identifiers (DIDs) on XRPL let accounts create and manage self-sovereign identity documents compliant with the W3C DID specification. Use DIDSet to create or update your DID document (e.g., public keys, service endpoints, verification methods), and DIDDelete to remove it when no longer needed.

🆔 Create / Update DID DIDSet
Data ✅ Required (JSON DID document or URI)
URI ➕ Optional (external DID document location)
Flags ➕ Optional (e.g., master key control flags)
🗑️ Delete DID DIDDelete
DID ID / Data ✅ Required (to identify which DID to remove)
Signer ✅ Must be authorized (account key or delegate)
Conditions ✅ No dependent objects blocking deletion
📝 Important Notes:
  • Requires the DID amendment to be enabled on the network.
  • The DID is anchored to your XRPL account address — the DID document is stored in a DID ledger object owned by the account.
  • Data field typically contains a compact JSON DID document (verificationMethod, authentication, service endpoints, etc.) — max size is limited (~1 KB compressed).
  • Alternatively, use URI to point to an external DID document (IPFS, HTTPS, etc.) for larger or mutable content.
  • Each DID object counts toward your account’s owner reserve (~0.2 XRP) until deleted.
  • DID documents are public once set — anyone can read them from the ledger.
  • Only the controlling account (or authorized delegate if set up) can update or delete the DID.

⚠️ Irreversibility & Control Risks

DID documents are tied to account control — losing key access can make your DID unusable or orphaned.

  • Once set, DID document data is **immutable until updated** — incorrect or outdated info requires another DIDSet transaction to fix.
  • If you lose control of the account (lost keys, no regular key/multi-sign backup), you **permanently lose the ability** to update or delete the DID — it remains on the ledger forever.
  • Deletion is only possible if no dependent objects (e.g., credentials or permissions referencing the DID) block it — check current amendment rules.
  • Public exposure of DID documents means sensitive endpoints or keys should not be included unless encrypted or hashed.
  • Reserve cost remains until deletion — deleting frees the reserve, but test deletion carefully to avoid accidental lockup.
  • Always test DID creation/update/deletion on devnet or Testnet first — wrong formats or oversized data cause tx failure and fee burn.

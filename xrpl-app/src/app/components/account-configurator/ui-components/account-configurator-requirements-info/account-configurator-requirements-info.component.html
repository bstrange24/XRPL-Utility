Account Flags (AccountSet)

AccountSet transactions let you configure account behavior by enabling (SetFlag) or disabling (ClearFlag) specific flags. These control payments, trust lines, security, issuance rules, and more.

⚙️ Enable Flag SetFlag
SetFlag ✅ Required (one per tx)
ClearFlag ❌ Optional (none or one)
Other fields (Domain, etc.) ➕ Optional
⚙️ Disable Flag ClearFlag
ClearFlag ✅ Required (one per tx)
SetFlag ❌ Optional (none or one)
tf Flags (in Flags field) ➕ Optional (some equivalents)
📝 Important Notes:
  • Use AccountSet with SetFlag to enable or ClearFlag to disable — only one of each per transaction.
  • Most flags start disabled; check your AccountRoot ledger entry (via account_info) to see current lsf* flags.
  • Some flags have strict requirements (e.g., no trust lines for asfRequireAuth, master key for asfDisableMaster or asfNoFreeze).
  • Flags like asfDisallowXRP are advisory only (clients should respect them, but protocol does not enforce).
  • Changes are irreversible for certain flags (see warnings below).
  • Transaction consumes a small fee even if no changes occur — always specify at least one flag or field.

⚠️ Irreversible & Restricted Flags

Some flags cannot be unset once enabled — use with caution!

  • asfNoFreeze: Permanently disables freezing trust lines or global freeze — irreversible; requires master key to set.
  • asfAllowTrustLineClawback: Permanently enables clawback on issued tokens — irreversible; requires no objects (trust lines, offers, etc.) to set.
  • asfAllowTrustLineLocking: Permanently allows escrow/locking of issued tokens — irreversible after enabling.
  • asfDisableMaster: Disables master key signing — can only be enabled with master key; disable via regular key or multi-sign.
  • asfRequireAuth: Can only be enabled if account has no trust lines or offers.
  • Always verify requirements and test on devnet — wrong flags can lock you out or limit functionality permanently.

Account Metadata (AccountSet)

Use AccountSet to attach public metadata to your XRPL account, such as a linked domain (for verification & token info), Gravatar hash, encrypted messaging key, transfer fees, and more. These fields appear in your AccountRoot ledger entry.

📋 Core Metadata Common Settings
Domain ➕ Optional (hex-encoded lowercase ASCII)
MessageKey ➕ Optional (33-byte public key for encrypted msgs)
📋 Advanced Metadata Issuer / Utility Fields
TransferRate ➕ Optional (billionths; e.g., 1200000000 = 20% fee)
TickSize ➕ Optional (3–15 or 0 to disable)
WalletLocator ➕ Optional (arbitrary 256-bit value)
NFTokenMinter ➕ Optional (authorized NFT minter address)
📝 Important Notes:
  • All metadata fields are optional in an AccountSet transaction — include only the ones you want to set or change.
  • To remove/clear a field, set it to an empty value (e.g., empty string for Domain/MessageKey, 0 for TransferRate/TickSize) or omit it if clearing isn't needed.
  • Domain: Must be hex of lowercase ASCII (e.g., "example.com" → "6578616D706C652E636F6D"). Max 256 bytes. Used for account verification via xrp-ledger.toml file on your domain.
  • MessageKey: Must be exactly 33 bytes (starting with 0x02/0x03 for secp256k1 or 0xED for Ed25519) — invalid format fails the tx.
  • TransferRate: For issuers only; valid values are 0 (no fee) or 1,000,000,000–2,000,000,000 (0–100%). Lower values invalid.
  • Changes take effect immediately upon successful ledger inclusion and cost a small transaction fee.

⚠️ Format & Irreversibility Considerations

Metadata is public and mostly permanent once set — choose carefully.

  • Fields like Domain and MessageKey are easily changeable, but incorrect formats cause transaction failure.
  • TransferRate and TickSize affect all holders of your issued assets — changing them can impact trust and liquidity.
  • Setting NFTokenMinter authorizes another account to mint NFTs for you (requires amendment); clear by omitting or using related flags.
  • WalletLocator has no protocol meaning — use it for custom data if desired, but it's visible on the ledger.
  • Always verify formats (e.g., hex encoding, byte lengths) before submitting — test on devnet or Testnet first to avoid wasting fees or misconfiguring your account.

Deposit Authorization (DepositAuth)

Deposit Authorization is an optional account setting that blocks all incoming payments (XRP or tokens) from unauthorized accounts. Once enabled, your account can only receive funds from preauthorized senders, checks you cash, escrows you finish, or if your balance falls below the reserve requirement.

🔒 Enable DepositAuth SetFlag
SetFlag ✅ Required (value: 9 / asfDepositAuth)
ClearFlag ❌ Optional (none)
Other AccountSet fields ➕ Optional
🔓 Disable DepositAuth ClearFlag
ClearFlag ✅ Required (value: 9 / asfDepositAuth)
SetFlag ❌ Optional (none)
Other AccountSet fields ➕ Optional
📝 Important Notes:
  • Requires the DepositAuth amendment to be enabled on the network (most mainnet instances have it).
  • Use AccountSet with SetFlag: 9 to enable or ClearFlag: 9 to disable — only one flag per transaction for this purpose.
  • Check current status via account_info — look for lsfDepositAuth (bit 0x01000000) in your AccountRoot flags.
  • When enabled, incoming Payment transactions fail unless: from a preauthorized account (via DepositPreauth), you finish an Escrow/Check, or your XRP balance is below reserve (allows top-up to reserve).
  • Preauthorizations use DepositPreauth transactions — each adds to your owner reserve (like trust lines or escrows).
  • Disabling is always possible with another AccountSet — no permanent lock-in for the flag itself.

⚠️ Strict Incoming Payment Block & Compliance

Enabling DepositAuth strictly prevents unwanted deposits — this is enforceable by the protocol (not advisory like DisallowXRP).

  • Once enabled, no one can send you XRP or tokens directly without your explicit preauthorization — useful for regulatory compliance or spam protection.
  • If no preauthorizations exist, your account effectively blocks all incoming payments under normal conditions (except reserve top-ups).
  • Failed incoming payments return tec codes (e.g., tecNO_PERMISSION) — sender loses fee but funds stay with them.
  • Preauthorizing many accounts increases your owner reserve cost — each DepositPreauth object reserves XRP until removed.
  • Use carefully: enabling without planning preauths can isolate your account from intended incoming funds. Test on devnet/Testnet first.

Multi-Signer Setup (SignerListSet)

Multi-signing allows multiple keys to authorize transactions for your account, useful for shared control, security, or institutional custody. Use SignerListSet to create, update, or delete your account's SignerList object, defining who can sign and the required quorum.

🗝️ Create / Update Signer List Add or Change Signers
SignerEntries ✅ Required (1–8 entries)
Quorum ✅ Required (1 to sum of weights)
MaxSigners ➕ Optional (default: sum of weights)
🗑️ Remove Signer List Delete Entire List
SignerEntries ❌ Empty array (or omit)
Quorum ❌ Set to 0
MaxSigners ❌ Optional (ignored)
📝 Important Notes:
  • SignerListSet replaces the entire signer list — you must provide the full current + desired list when updating.
  • Up to 8 signers max (each with a weight 1–255); total weight sum can be any value, but quorum must be ≤ sum and ≥1 (unless deleting).
  • Each signer is a regular key or keyset address — master key cannot be a signer.
  • Creating or updating a SignerList increases your account’s owner reserve (typically ~2 XRP base + ~0.2 XRP per signer object).
  • Multi-sign transactions use MultiSign field instead of Sequence; they consume a higher fee and must meet the quorum.
  • To use multi-signing, your account must have a SignerList set — transactions signed by a single key (master or regular) will still work unless you also disable the master key.

⚠️ Irreversible Aspects & Security Risks

Mistakes in signer setup can lock you out of your account — plan carefully.

  • If you delete your master key (via asfDisableMaster) and have no working signers/quorum, you permanently lose control of the account.
  • Signer weights and quorum are not easily reversible without another SignerListSet tx — always keep access to enough signers to meet quorum.
  • Adding malicious or lost-key signers can prevent you from signing transactions if quorum becomes unreachable.
  • SignerList objects count toward owner reserve — removing signers frees reserve only after the list is updated/deleted.
  • Multi-sign txs are more expensive and slower to confirm — use for high-value or shared-control scenarios only.
  • Test thoroughly on devnet/Testnet: simulate quorum failures, key losses, and reserve costs before mainnet deployment.

Modify RegularKey (SetRegularKey)

A Regular Key is a secondary key pair that can sign transactions for your account instead of (or in addition to) the master key. Use SetRegularKey to assign a new regular key, change an existing one, or remove it entirely — great for security if your master key is exposed or for daily use without risking the master.

🔑 Assign / Change RegularKey Set New Key
RegularKey ✅ Required (base58-encoded address)
Other fields ❌ None needed
Signer ➕ Master key or current regular key
🗑️ Remove RegularKey Clear Existing
RegularKey ❌ Omit field (or empty)
Other fields ❌ None needed
Signer ➕ Master key or current regular key
📝 Important Notes:
  • SetRegularKey transaction assigns/changes/removes the regular key — it stores the address in your AccountRoot's RegularKey field.
  • The RegularKey must be a valid XRPL address (base58-encoded) with a known secret — it does not need to be an activated/funded account.
  • You cannot set RegularKey to match your master key address (blocked by amendment fixMasterKeyAsRegularKey to prevent blackholing).
  • Signing: First assignment usually requires master key; changes/removals can use master or current regular key.
  • Regular key signs normal transactions just like master — but multi-sign or asfDisableMaster changes behavior.
  • No direct reserve cost for the regular key itself (unlike SignerList or trust lines), but related setups (e.g., disabling master) have implications.

⚠️ Security & Lockout Risks

RegularKey changes are powerful but can permanently lock you out if mishandled — especially with master key disabled.

  • If you disable master key (asfDisableMaster) and lose access to your regular key (or set none), you permanently lose control — no recovery possible.
  • Compromised regular key? Change or remove it immediately using master key (or multi-sign if set up) to regain control.
  • Never set RegularKey to an unknown/lost secret — test signing with the new key before relying on it or disabling master.
  • Removing regular key is reversible (just assign a new one), but combined with disabled master or no signers, it's irreversible lockout.
  • Always verify the address format and test on devnet/Testnet — wrong key means failed transactions or lost access.
  • If using for security: Keep master key offline/secure; use regular key for daily ops; consider multi-sign for extra redundancy.
